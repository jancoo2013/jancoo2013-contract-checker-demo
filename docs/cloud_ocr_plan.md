# План Cloud OCR для публичного демо

## Почему серверный Tesseract не подходит

Серверный Tesseract был отключён в публичном Streamlit-демо, потому что на реальных многостраничных договорах он оказался слишком медленным и нестабильным. В Streamlit Cloud такие задачи могут зависать, долго занимать ресурсы приложения и ухудшать UX даже для пользователей, которые хотят просто вставить уже готовый текст.

Дополнительная проблема — тяжёлые системные зависимости: отдельный бинарный Tesseract, языковые пакеты Hebrew/English, Python-обвязки и библиотеки обработки изображений. Для публичного демо лучше сохранить лёгкий и предсказуемый запуск.

## Целевая архитектура

Целевой поток остаётся простым и разделённым по слоям:

```text
фото страниц договора
→ Cloud OCR backend/provider
→ нормализованный текст
→ deterministic contract analyzer
→ отчёт для ручной проверки
```

OCR отвечает только за извлечение текста из изображений. Детерминированный анализатор отвечает только за поиск известных полей, предупреждений и зон ручной проверки. Эти слои не должны смешиваться.

## Провайдер-независимый формат результата

В `contract_checker/cloud_ocr.py` подготовлен нейтральный формат, который не привязан к конкретному SDK:

- `CloudOCRPageResult` — результат по одной странице:
  - `page_index`;
  - `filename`;
  - `raw_text`;
  - `blocks`;
  - `success`;
  - `error`;
  - `provider`;
  - `confidence`.
- `CloudOCRContractResult` — результат по договору целиком:
  - `raw_text`;
  - `pages`;
  - `success`;
  - `error`;
  - `provider`.

Текст многостраничного договора объединяется через явные разделители вида:

```text
--- СТРАНИЦА 1: filename.jpg ---
<text>
```

Так анализатор и пользователь видят границы страниц, а будущие OCR-провайдеры могут сохранять дополнительные блоки в `blocks` без изменения основного пайплайна.

## Планируемые провайдеры

Планируемые Cloud OCR провайдеры:

1. Google Cloud Vision OCR.
2. Azure AI Vision Read OCR.

Сейчас обе функции являются заглушками. Они не импортируют Google/Azure SDK, не читают секреты, не делают сетевые запросы и возвращают понятное русское сообщение о том, что провайдер не настроен.

## Как секреты будут использоваться позже

Когда платный OCR будет включён, ключи должны храниться только в защищённой конфигурации, например в Streamlit secrets:

- ключи нельзя коммитить в GitHub;
- нельзя добавлять service account JSON в репозиторий;
- нельзя показывать ключи в UI;
- нельзя писать ключи в логи или отчёты;
- локальные примеры должны использовать `.gitignore` и безопасные шаблоны без реальных значений.

Будущая реализация должна сначала проверить наличие секретов, затем создать клиента провайдера, выполнить OCR и вернуть результат в нейтральном формате `CloudOCRContractResult`.

## OCR JSON как мост

Пока Cloud OCR не подключён, рабочим мостом остаётся загрузка OCR JSON от внешнего распознавателя. Пользователь может распознать договор вне приложения, загрузить JSON с текстом, проверить и исправить извлечённый текст, а затем запустить тот же детерминированный анализ.

## Рукописный иврит остаётся недоверенным

Рукописный иврит не считается автоматически подтверждённым источником даже после подключения Cloud OCR. Если важный пункт договора виден только в рукописной форме или распознан с сомнением, приложение должно направлять пользователя к ручной проверке и юридической консультации.

## Детерминированный анализатор остаётся отдельным

Cloud OCR не должен менять логику проверки договора. Анализатор остаётся детерминированным: он получает текст, ищет ожидаемые поля и рискованные формулировки, формирует отчёт и не делает LLM-вызовы. Это сохраняет публичное демо прозрачным, дешёвым и воспроизводимым.
